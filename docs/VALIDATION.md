## CSS配置変更と配信比較（2026年10月30日）

`global.css`に集中していたページ／コンポーネント固有の規則を、記事本文の`content.css`、Astroコンポーネント、該当ページへ分けました。現在は`global.css`が245行、`content.css`が311行です。100文字を超えるTailwindクラス属性は0件になりました。共通トークン、リセット、全ページ共通レイアウト、共有案内パネルは共通側に残し、Tailwind CSS v4は短い単純なユーティリティに使います。vanilla-extractはAstroスコープCSSとの比較で3ページのHTML+CSS gzipに5%の改善がなかったため採用しません。

Astroの`inlineStylesheets: 'auto'`と`'always'`を最終ソースで切り替え、各方式5回交互にLighthouseで測定しました。次表は5回のLCP中央値です。

| ページ       |   auto | always | alwaysとの差 |
| ------------ | -----: | -----: | -----------: |
| トップ       | 2182ms | 2181ms |         -1ms |
| 記事         | 2255ms | 2258ms |         +3ms |
| プロジェクト | 2256ms | 2332ms |        +76ms |

いずれも各ページの悪化許容幅（100msまたは5%の大きい方）内でした。`always`の初回HTML+CSS gzipはページあたり51〜372B小さくなりますが、CSSをキャッシュした再訪では`auto`が約6.2〜6.5KB小さくなるため、`auto`を採用しました。

基準コミット`57d8ccb`と最終`auto`版の交互5回測定は次のとおりです。

| ページ       | 基準版LCP中央値 | 最終版LCP中央値 |    差 |
| ------------ | --------------: | --------------: | ----: |
| トップ       |          2180ms |          2181ms |  +1ms |
| 記事         |          2257ms |          2256ms |  -1ms |
| プロジェクト |          2333ms |          2256ms | -77ms |

ローカルgzip応答のHTML+CSS合計では、初回はトップ20,178→22,434B（+2,256B）、記事13,143→13,430B（+287B）、プロジェクト13,360→13,208B（-152B）でした。ハッシュ付き共通CSSをキャッシュした再訪では、トップ20,178→15,889B（-4,289B）、記事13,143→6,885B（-6,258B）、プロジェクト13,360→6,663B（-6,697B）です。トップから記事・プロジェクトを閲覧する合計は46,681→35,982Bとなり、10,699B減りました。これは同一条件のローカルgzip比較であり、Cloudflare本番配信のBrotli転送量ではありません。

比較用スクリプトは`bun scripts/compare-css-performance.ts <基準dist> <比較dist> <回数>`です。LCPの各回・中央値とgzip転送量を`artifacts/css-migration/performance/`に保存しています。このディレクトリは`.gitignore`対象のため、再現条件と数値をこの記録にも転記しました。

最終版で`bun run lint`、`bun run check`（55ファイル、エラー・警告・ヒントなし）、`bun run build`と生成物検証が成功しました。`bun run test:e2e`は24件成功、3件スキップです。スキップされた記事目次・コード関連の3件は、公開記事に対象コードブロックがないためです。既存E2Eは320、375、768、1280pxのライト／ダークを確認しました。追加で10ページを1023・1440px、ライト／ダークで開き、40通りすべてで横スクロール・主要領域の欠落がないことを確認しました。トップ・記事・プロジェクトは375・1440pxで旧スクリーンショットと比較し、移行後の差分は概ね0〜0.03%（色差しきい値45）でした。
