# 運用・障害対応・引き継ぎ

## 権限と担当

- 代表・管理責任者：GitHub Organization、Cloudflare、ドメインの管理。
- Webサイト管理担当：コード・設定のレビュー、公開、障害復旧。
- 記事編集担当：記事の内容・掲載許可の確認。
- 一般部員：ブランチ作成、記事執筆、PR提出。

記事執筆者へCloudflare管理権限を一律付与しません。管理者は2名以上を確保し、多要素認証と復旧手段を管理します。担当者名・チーム名・連絡方法はOrganization内の管理記録に残してください。

## 日常の確認

公開後は変更ページ、記事一覧、検索、RSS、画像を確認します。ビルドログでエラーがないことを確認します。独自のアクセス解析は導入していません。

依存関係の更新PRは週次で確認し、CI・表示・検索が成功してからマージします。TypeScriptは`astro check`の対応状況に合わせて更新してください。現在はTypeScript 6を使用しています。

## CIが失敗した場合

1. Biome・MDX検査：ローカルで`bun run lint`を再現します。必要なら`bun run format`後に差分を確認します。
2. スキーマ検証：Frontmatter、タグ、著者参照、画像の代替テキスト、ファイル名を修正します。
3. ビルド・検索：`bun ci`から再現し、Node・BunのバージョンとPagefindのログを確認します。
4. 内容を修正してPRへPushし、再レビューを受けます。

## Pagesのビルドが失敗した場合

正常なデプロイを維持します。依存関係・環境変数・`SITE_RELEASE`・公開コンテンツ検証のログを確認します。CI成功を理由に必須チェックを無効化しません。

## 公開後に問題が見つかった場合

1. PagesのDeploymentsから直前の正常な本番デプロイへロールバックします。
2. 公開URLで復旧を確認します。
3. 原因となった変更をGitのRevert用PRで戻すか、修正PRを作成します。
4. CI・プレビュー・レビュー後に再公開します。
5. 影響範囲、復旧方法、再発防止を管理記録に残します。

トークンや個人情報を誤って公開した場合、サイトの取り下げだけでなく元リポジトリ・Git履歴・キャッシュの扱いも確認します。認証情報は直ちに失効・再発行します。

## 年度交代時

- OrganizationのOwners、CODEOWNERS、ルールセット、公開担当を確認する。
- Cloudflare、DNS、ドメイン更新担当、支払い・連絡先、復旧手段を引き継ぐ。
- 不要な権限を削除し、後任者の環境で固定インストール・ビルド・プレビューを確認する。
- 記事1件のPRから公開までを実演する。
- Pagesのプロジェクト名、環境変数、ブランチ設定、独自ドメイン、ロールバック先を確認する。
- 掲載許可と著者プロフィール、連絡先、入部情報を見直す。

## プライバシー変更

問い合わせフォーム、アクセス解析、外部埋め込みなどを追加するときは、データ送信先と保存内容を確認し、プライバシーポリシーを更新してください。
