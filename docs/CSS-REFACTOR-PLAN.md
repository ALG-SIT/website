# CSS整理・性能改善の実行計画

## 目的

CSSをファイル単位で小さくすることだけを目的にせず、スタイルの責務を明確にし、表示を保ったまま初回表示とキャッシュ後の転送量を改善する。変更の効果は、同一条件のベースラインと比較して判断する。

## 現状と設計判断

- 基準コミットは `57d8ccb`。現在の作業ツリーにはCSS分割とページ改修が含まれるため、作業を始める前にその差分を保存・確認し、既存変更を上書きしない。
- `src/styles/global.css` は約1,700行から245行へ縮小済み。共有トークン、リセット、全ページ共通の基礎スタイルを残す。
- `src/styles/content.css` に記事本文のスタイルを分離済み。Markdown固有の表示はここに集約する（現在311行）。
- `PostCard`、`ProjectCard` はAstroコンポーネント内のスコープ付きCSSを使う。比較したvanilla-extract案はHTMLとCSSのgzip合計が3ページで約0.05%以下の差にとどまり、5%の採用基準を満たさなかったため、依存とビルドプラグインを追加しない。
- 現在はTailwind CSS v4が有効で、Astroの`inlineStylesheets`は`auto`。Tailwindは短い単純なレイアウト・間隔・表示ユーティリティに限定し、長い任意値のクラス列や複数箇所で繰り返す表現は意味のあるコンポーネント／ページCSSへ移す。Tailwindの一括撤去は行わない。
- `.container`、`.page-shell`、`ButtonLink`など共有表現を導入済み。以降も重複が確認できた場合だけ共有化し、単発のスタイルまで抽象化しない。
- 最終ソースで`auto`と`always`を5回交互測定し、LCP中央値の差はトップ-1ms、記事+3ms、プロジェクト+76ms。許容幅内で、`auto`はキャッシュ後の再訪転送量が6.2〜6.5KB小さいため維持する。

## 作業フェーズ

### 0. 比較条件の固定

1. 基準コミットと現行作業ツリーのソース・設定・生成物サイズを記録する。
2. 代表ページをトップ、記事詳細、プロジェクト詳細に固定し、各URL・ビューポート・テーマ・キャッシュ条件を記録する。
3. 5回以上、ベースラインと変更版を交互に測定する。ウォームアップ、端末条件、ネットワーク条件を統一し、LCPの中央値とばらつきを保存する。
4. Lighthouseの数値だけで結論を出さず、HTML gzip、CSS gzip、初回転送、キャッシュ済み遷移の転送量も別々に記録する。

### 1. スタイル配置ルールの確定

| スタイルの種類                                             | 配置先                                    |
| ---------------------------------------------------------- | ----------------------------------------- |
| 色・余白など全体の設計トークン、リセット、最小限の共通要素 | `src/styles/global.css`                   |
| Markdown/MDX本文、コード、表、見出しアンカー               | `src/styles/content.css`                  |
| 再利用コンポーネント固有の見た目                           | 対応する`.astro`内のスコープ付き`<style>` |
| ページ固有のヒーローやレイアウト                           | 対応するページのスコープ付き`<style>`     |
| 単純で短い一度限りのレイアウト・間隔                       | Tailwindユーティリティ                    |
| 複数ページで使うボタン・コンテナなど                       | 共有コンポーネントまたは名前付きクラス    |

Tailwindクラスは要素の見た目を追える長さに保つ。任意値の長いクラス列、重複するクラス列、状態・ブレークポイントが複雑なクラス列はCSSへ移す。既存の視覚差を避けるため、一度に一つのコンポーネントまたはページ群を移行する。

### 2. 残るCSSとクラスの整理

1. 全`.astro`のクラスを一覧化し、長いクラス列・重複パターン・未使用CSSを優先順位付けする。
2. 共通コンポーネント（ヘッダー、カード、ボタン、パンくず等）を一群ずつ整理する。
3. 固定ページ、一覧ページ、詳細ページの順に、各ページ固有CSSとTailwindユーティリティの境界を整える。
4. 記事本文の見出し、リンク、リスト、画像、コード、表を代表コンテンツで確認する。
5. `!important`追加で回避せず、原因となるカスケード・レイヤー・セレクターを直す。
6. Tailwindを残す箇所がなくなった場合に限り、依存・Viteプラグイン・ディレクティブを削除する。現行計画では全面撤去を前提としない。

### 3. CSS配信方式の確定

`inlineStylesheets: 'always'`と`'auto'`を同じソース・同じ条件で比較する。初回ページではHTML+CSSの合計転送量、キャッシュ後は共通CSSを再取得しない場合の転送量を評価する。現行設定の`auto`を暫定維持し、後述のLCP基準を満たさない場合にだけ設定を見直す。出力検証は、インラインCSSまたは同一オリジンの生成CSSファイルの双方を検査できる状態にする。

### 4. 表示・機能・性能の検証

- ビューポート：320、375、768、1023、1440px。
- テーマ：ライト、ダーク。トップ、記事詳細、プロジェクト詳細に加え、ナビゲーション、カード、ボタン、記事本文を確認する。
- E2E、コンテンツ検証、型検査、lint、生成物検証を実行する。既存テストにない代表コンテンツは、利用できる実データまたは固定fixtureで確認する。
- LCPを5回以上交互測定し、中央値と各回の結果を保存する。`inlineStylesheets`の候補比較も同じビルド条件で行う。
- 比較画像は同一ブラウザ・同一フォント読込完了後に撮影し、差分画像だけでなくレイアウト寸法と手動目視を併用する。

## 合格条件と停止条件

| 項目                  | 合格条件                                                                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 機能                  | lint、型検査、コンテンツ検証、build、生成物検証、E2Eが成功する。既存の意図した機能に回帰がない                                              |
| 表示                  | 指定幅・両テーマでクリッピング、意図しない折返し、重なり、操作不能がない。主要領域の差分は原因を説明でき、意図した変更として承認可能        |
| LCP                   | 代表ページごとにベースライン中央値から100msまたは5%の大きい方を超えて悪化しない                                                             |
| 転送量                | 初回HTML+CSS gzipとキャッシュ後転送量を両方報告する。移行対象ページの合計が基準版を超える場合、増加原因と相殺効果を明記してから次段階へ進む |
| vanilla-extract再検討 | 3ページ以上で、表示・機能が同等かつHTML+ロードCSS gzip合計がAstroスコープCSSより5%以上小さく、LCP基準も満たす場合のみ再評価                 |

いずれかの表示または性能ゲートを外れた場合、その段階の変更を切り分けて原因を直し、同条件で再測定する。根拠のない差分許容や合格扱いはしない。

## 完了時の成果物

- 責務ごとに整理されたスタイルと、`docs/IMPLEMENTATION.md`の更新済み配置方針。
- ベースライン／最終版のビルド条件、HTML・CSS gzip、キャッシュ時転送量、LCP測定値をまとめた検証記録。
- 表示確認のスクリーンショットと差分、実行した自動検証の結果。
- Tailwindを残す場合は用途と境界、vanilla-extractを採用しない場合は比較結果を記録する。

## 実施順

1. 比較条件と記録先を固定する。
2. スタイル配置ルールに沿って一群ずつ整理し、各群で表示確認する。
3. CSS配信候補を比較して設定を確定する。
4. 全検証と最終5回測定を行い、基準を満たさない箇所を修正する。
5. 実装方針と測定結果を文書化して完了とする。

## 実行結果（2026年10月30日）

- フェーズ0：基準コミット`57d8ccb`と最終ソースをgzip配信で5回交互測定。トップ／記事／プロジェクトのLCP差は+1ms／-1ms／-77msで、各ページの許容幅内。
- フェーズ1：責務別配置を適用。global 245行、content 311行、コンポーネント／ページ固有のスタイルは各`.astro`へ配置。vanilla-extractは3ページの転送量で5%改善しなかったため不採用。
- フェーズ2：カード、ボタン、ヘッダー、検索、ホーム、記事一覧・詳細、プロジェクト詳細などの繰り返し・複雑なクラス列を名前付きCSSへ移動。100文字超のclass属性は0件。短いTailwindユーティリティとTailwind本体は維持。
- フェーズ3：`inlineStylesheets: 'auto'`を選定。`always`は初回gzipが51〜372B小さいが、キャッシュ後は`auto`が6.2〜6.5KB小さい。LCP中央値は`always`が最大76ms遅く、許容範囲内。
- フェーズ4：lint、型検査、build、生成物検証が成功。E2Eは24件成功／3件スキップ。320・375・768・1280pxのE2Eに加え、1023・1440pxを10ページ・2テーマで確認し、40通りすべて横スクロールなし。375・1440pxの画像比較は概ね0〜0.03%の差。

初回HTML+CSS gzipは基準版よりトップ2,256B、記事287B増え、プロジェクト152B減った。CSSキャッシュ後の再訪はページごとに4,289〜6,697B減り、トップ→記事→プロジェクトの合計では基準版46,681Bから最終35,982Bへ10,699B減った。LCP、転送量、テストの詳細は[検証記録](VALIDATION.md#css配置変更と配信比較（2026年10月30日）)に記載。

以上でこの計画の実行と検証を完了した。Cloudflare本番CDNのBrotli転送量と実ユーザーのLCPは今回のローカルgzip／Lighthouse比較には含めていない。
